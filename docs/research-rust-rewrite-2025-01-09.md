# slang-sukimasim Rust 書き換え調査レポート (2025-01-09)

## エグゼクティブサマリー

**結論: 完全な Rust 書き換えは非推奨。FFI 統合を推奨。**

| 選択肢 | 推奨度 | 理由 |
|--------|--------|------|
| 完全 Rust 書き換え | ❌ 非推奨 | 工数膨大 (5-10人年)、リスク高、ROI 低 |
| FFI 統合 (Autocxx/CXX) | ✅ 推奨 | slang の品質を活用、Rust コアと組み合わせ |
| sv-parser 利用 | ❌ 不十分 | パーサーのみ、セマンティック解析なし |

---

## 1. 既存の Rust SystemVerilog パーサー

### 1.1 sv-parser (dalance/sv-parser)

**概要:**
- GitHub: https://github.com/dalance/sv-parser
- 458 stars, 64 forks, 604 commits
- 純粋な Rust で書かれた SystemVerilog パーサー

**IEEE 1800 準拠レベル:**
- IEEE 1800-2017 に「完全準拠」と主張
- Annex A (Formal syntax) に従った CST を生成
- プリプロセッサ（マクロ展開、インクルード処理）をサポート

**機能:**
- 構文解析のみ（エラボレーション、型チェックなし）
- トークン位置情報の追跡
- CST（Concrete Syntax Tree）の生成

**依存プロジェクト:**
- svlint: SystemVerilog リンター
- svls: Language Server 実装
- morty: ソースファイルシリアライゼーション

### 1.2 sv-parser vs slang 比較

| 項目 | sv-parser (Rust) | slang (C++) |
|------|------------------|-------------|
| IEEE 標準 | 1800-2017 | **1800-2023** |
| 機能範囲 | パーサーのみ | **完全なフロントエンド** |
| エラボレーション | ❌ なし | ✅ あり |
| 型チェック | ❌ なし | ✅ あり |
| エラー回復 | 基本的 | **堅牢、エディタ向け** |
| テストスイート | 限定的 | **sv-tests 最高合格率** |
| 成熟度 | 中程度 | **非常に高い** |

### 1.3 結論

**sv-parser では slang の代替にならない。**

シミュレータには完全なセマンティック解析が必要であり、sv-parser はその機能を持っていない。

## 2. C++/Rust FFI オプション

### 2.1 CXX Crate

- [cxx.rs](https://cxx.rs/)
- 安全な双方向 C++/Rust 相互運用
- ゼロオーバーヘッド FFI
- `#[cxx::bridge]` マクロで境界を宣言

**制限:**
- 手動でインターフェースを定義する必要がある
- slang の約 250 個のパブリック API を手動で定義する必要

### 2.2 Bindgen

- [rust-lang/rust-bindgen](https://github.com/rust-lang/rust-bindgen)
- C/C++ ヘッダーから自動的に Rust FFI バインディング生成
- 生成されるのは unsafe な FFI コード

### 2.3 Autocxx (推奨)

- [google/autocxx](https://github.com/google/autocxx)
- **自動バインディング生成** + cxx の安全性
- 大規模 C++ コードベースに適している

### 2.4 FFI アプローチ比較

| アプローチ | 自動生成 | 安全性 | C++ 機能カバレッジ | 作業量 |
|-----------|---------|-------|-------------------|-------|
| CXX | 手動 | 高 | 限定的 | 非常に高い |
| Bindgen | 自動 | 低 (unsafe) | 中程度 | 低い |
| Autocxx | 自動 | 中〜高 | 中程度 | 中程度 |

## 3. slang コードベースの複雑性

### 3.1 コード規模

| ディレクトリ | 行数 |
|-------------|------|
| source/ast/ | **56,299 行** |
| source/ 合計 | **118,164 行** |
| include/ | 30,897 行 |
| tests/ | 55,985 行 |
| **全体合計** | **約 253,000 行** |

### 3.2 主要コンポーネント

```
source/
├── ast/           # エラボレートされた AST (56k 行) - 最大
│   ├── symbols/   # シンボル定義 (60+ クラス)
│   ├── types/     # 型システム (15+ クラス)
│   ├── expressions/ # 式 (30+ クラス)
│   └── statements/  # ステートメント (15+ クラス)
├── parsing/       # レキサー、プリプロセッサ、パーサー (16k 行)
├── syntax/        # 構文木 (3k 行)
├── analysis/      # データフロー解析等 (3k 行)
└── numeric/       # SVInt 等の数値処理 (3k 行)
```

### 3.3 技術的な複雑性

- `std::` 使用: **1,942 箇所**
- テンプレート使用ファイル: **133 ファイル**
- 仮想関数: **43 箇所**
- C++20 機能: **178 箇所**

## 4. 大規模 C++ プロジェクトの Rust 書き換え事例

### 4.1 Mozilla Stylo (Firefox CSS エンジン) - 成功事例

**タイムライン:**
- 2015年: プロジェクト構想開始
- 2016年4月: 最初のピクセル描画
- 2016-2017年: **15ヶ月のプロダクション化作業**
- 2017年11月: Firefox Quantum としてリリース

**チーム規模:**
- 最初の数ヶ月: 2-3人
- その後: **10カ国以上からのスタッフとボランティア**

**セキュリティ効果:**
- 69 件のセキュリティバグのうち **51 件 (73.9%)** が Rust により防止可能
- 重大/高深刻度バグ 34 件中 **32 件 (94%)** がメモリ関連

**教訓:**
1. インクリメンタル移行が鍵
2. 論理エラーは防げない（メモリ安全性のみ）
3. テスト必須（過去のバグを再導入するリスク）
4. 「飛行中のジェットエンジン交換」の困難さ

### 4.2 他の事例

| プロジェクト | 内容 | 結果 |
|-------------|------|------|
| Discord | Go → Rust | 成功、パフォーマンス改善 |
| Figma | サーバーコード | 成功 |
| Linux Kernel | Rust ドライバーサポート | 進行中 |

### 4.3 失敗パターン

1. **複雑性の過小評価**: エッジケース処理が見えない
2. **「第二システム効果」**: 過剰な機能追加
3. **知識の喪失**: 暗黙知がドキュメント化されていない
4. **Rust の学習曲線**: 借用チェッカーと所有権

## 5. slang 完全書き換えの工数見積もり

### 5.1 推定工数

| シナリオ | 工数 | 備考 |
|---------|------|------|
| 楽観的 | 3-5 人年 | 経験豊富なチーム |
| 現実的 | **5-10 人年** | 一般的なケース |
| 厳密 | 10+ 人年 | Firefox 規模の品質要求 |

### 5.2 リスク要因

- **25万行以上のコード**: 膨大な規模
- **IEEE 1800-2023 の完全準拠**: 専門知識が必要
- **C++20 機能の多用**: 直接変換が困難
- **テストの移植**: 56,000行のテストコード
- **バグの再導入**: slang の蓄積されたバグ修正の喪失

## 6. 推奨アーキテクチャ

### 6.1 推奨: ハイブリッドアプローチ

```
┌─────────────────────────────────────────┐
│           sukimasim (Rust)              │
│  ┌─────────────────────────────────┐    │
│  │    シミュレータコア (Rust)       │    │
│  │  - イベント駆動エンジン          │    │
│  │  - スケジューリング              │    │
│  │  - 並列実行                     │    │
│  └─────────────────────────────────┘    │
│                  ↕ FFI (Autocxx/CXX)    │
│  ┌─────────────────────────────────┐    │
│  │        slang (C++)              │    │
│  │  - パーサー                     │    │
│  │  - エラボレーション              │    │
│  │  - 型チェック                   │    │
│  │  - AST 生成                    │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

### 6.2 段階的アプローチ

**Phase 1: FFI 統合**
- Autocxx で slang の主要 API を Rust に公開
- JSON AST 出力も代替手段として検討

**Phase 2: シミュレータコア開発**
- イベント駆動エンジンを Rust で新規開発
- slang をフロントエンドとして使用

**Phase 3: 必要に応じた最適化**
- ボトルネックがあれば個別コンポーネントを Rust で再実装

---

## 7. 最終結論

### 7.1 完全 Rust 書き換えは非推奨

**理由:**
1. **工数の膨大さ**: 5-10 人年、専任チームが必要
2. **slang の高品質**: 既に IEEE 1800-2023 完全準拠
3. **リスク**: バグ再導入、知識喪失、スケジュール超過
4. **ROI の低さ**: 書き換えの利点が限定的

### 7.2 推奨アプローチ

1. **slang を C++ フロントエンドとして維持**
2. **シミュレータコアを Rust で新規開発**
3. **FFI (Autocxx/CXX) で slang と接続**

これにより:
- slang の IEEE 準拠性とパフォーマンスを活用
- Rust のメモリ安全性をシミュレータコアで享受
- 開発リソースを効率的に配分
